## 3. 論点A: 方向 flag は測定アーティファクト (2 ヶ月連続)

月次 governance が `inspect_direction_logic` を発火 (UGH が technical 比 −13.6pt)。
FLAT 予測 19 観測を除いて同一日比較すると評価が反転する:

| 集計 | UGH | technical |
|---|---|---|
| 全 88 obs | 53.4% | 68.2% |
| **FLAT 除外 69 obs (同一日)** | **68.1%** | 66.7% |
| 7/30 暴落日も除外 | 70.1% | — |

FLAT 予測は up/down 実現に対し機械的に miss になるため、退避を多用した月ほど
方向率が沈む。**方向ロジック自体に欠陥はなく、むしろ baseline を上回っている。**

ただし flag を「誤報」として閉じるのは誤り。FLAT 19 観測の実態は退避判断の質の問題で
あり、7/13 (+53.2bp を FLAT で取りこぼし) のような実害がある。論点は方向ロジック
ではなく **退避ポリシー** に移す (→ §7 と併せて brief 化)。

**提案**: governance に `direction_hit_excl_flat` を追加し、閾値判定をそちらに移す。
FLAT 日は別指標 (FLAT 日の実現 |Δ| 分布 + range_hit) で評価する。engine 変更なし、
scoreboard / monthly_review の集計層のみ。brief 1 本相当。

## 4. 論点B: レンジ較正の崖 — 処方箋が定量化された

`expected_range` の包含率を実現変動幅で層別すると、明確な閾値構造が出た:

| \|実現Δclose\| | range_hit | N |
|---|---|---|
| < 15bp | **71%** | 48 |
| 15–30bp | 50% | 8 |
| 30–100bp | **0%** | 28 |
| ≥ 100bp | **0%** | 4 |

**30bp を超えた日は 32 観測すべてでレンジを外している。** 幅そのものを比較すると:

| 指標 | 値 |
|---|---|
| 実現幅 / 期待幅 の中央値 | **1.50x** |
| 同 平均 | 1.84x |
| 同 最大 (7/30) | **7.3x** (期待 78.8pips vs 実現 577pips) |
| 同 次点 (7/2) | 6.0x |

- 中央値 1.50x は「`range_width_scale` を 2.0 → 3.0 にすれば平時は包含できる」ことを
  意味する。**ただし定数倍では tail (6–7x) は原理的に捉えられない。**
- 本筋は realized volatility 連動のスケーリング。7/30 は前日 (7/29) に −26.9bp の
  先行下落と vol=normal→high の遷移があり、**vol 上昇を width に伝播させる経路**が
  あれば少なくとも部分的には拡がったはず。
- ENGINE-P3B (`range_width_scale=2.0` 固定) の設計判断を見直す spec 改訂 + brief。

## 5.5 【最重要】根本原因: conviction の二重役割が逆向きに効いている

§4 (レンジ) と §5 (magnitude) は別々の較正ミスではなく、**単一の構造的欠陥**の
二つの症状だった。4–7 月の 60 観測で相関を取ると:

| 相関 | 値 | 意味 |
|---|---|---|
| conviction ↔ expected \|Δ\| | **+0.501** | 設計どおり (確信が高いほど大きく予測) |
| conviction ↔ **実現** \|Δ\| | **−0.282** | **符号が逆。確信が低い日ほど大きく動く** |
| expected \|Δ\| ↔ 実現 \|Δ\| | **−0.159** | magnitude 予測に実力がない (弱い逆相関) |
| expected 幅 ↔ 実現 幅 | **+0.026** | レンジ幅予測は**完全な無相関** (ノイズと同等) |

conviction 3 分位で見ると症状が明白:

| conviction | expected \|Δ\| | 実現 \|Δ\| | 乖離 |
|---|---|---|---|
| 低 (0.27–0.61) | 4.7bp | **32.0bp** | **6.8 倍の過小** |
| 中 (0.61–0.74) | 9.2bp | 15.1bp | 1.6 倍 |
| 高 (0.74–0.95) | 10.4bp | 18.5bp | 1.8 倍 |

**エンジンが最も小さく予測する日に、市場は最も大きく動いている。** 7/30 はその
極端例 (conviction 0.325 → expected 6.4bp → 実現 236.9bp)。

### なぜこうなるか (理論的解釈)

conviction は「方向予測の信頼度」として設計され、実際その役割では正しく較正されて
いる (§6)。しかし PR #112 で明文化された **magnitude scaler としての第二の役割**は、
金融的には逆向きである: 相場は**不確実性が高い局面ほど大きく動く**。確信度と
変動量は同じ軸ではなく、conviction で magnitude をスケールするのはカテゴリエラー。

PR #112 は「dormant↔magnitude は Option B (decouple) を記録」として選択肢を残して
いた。**今回のデータはその decouple を実行すべき根拠になる。**

### 処方箋の検証 (定量済み)

magnitude / range 幅は**そもそも予測できない**ことも確認した — ボラティリティの
クラスタリングすら USDJPY 日足には無い (corr(前日幅, 当日幅) = +0.063)。
したがって**予測を諦め、統計的カバレッジに置き換える**のが正しい設計になる。

「直近 5 営業日の平均実現幅 × 1.5」を expected_range の半幅に用いた場合 (4–7 月、
77 日で検証):

| 実現 \|Δclose\| | 現行方式 | **新方式** |
|---|---|---|
| < 30bp | 71% | **100%** |
| 30–100bp | **0%** | **88%** |
| ≥ 100bp (7/30 のみ) | 0% | 0% |
| 全体 | 45.5% (7月) | **96%** |

- 中変動帯 (30–100bp) が **0% → 88%** と劇的に改善。全体で 96%。
- **テール (≥100bp) は新方式でも捉えられない。** 7/2 (92.9bp) と 7/30 (236.9bp) の
  2 日は包含外。これは欠陥ではなく、**カバーしないことを設計として明示すべき**領域
  (レンジに信頼水準を付し、テールは別建てのリスク警告で扱う)。

### 結論: 見直しが必要なのは方向ロジックではなく出力幅の生成経路

| 層 | 判定 | 根拠 |
|---|---|---|
| 方向予測 | **維持** | FLAT 除外で 68.1%、baseline 超え (§3) |
| conviction (信頼度として) | **維持** | ≥0.7 で 86% / <0.7 で 40% と正しく較正 (§6) |
| conviction → magnitude scaler | **据え置き** | 逆符号 (−0.282) だが §5.6 で代替 5 案が全て close error を改善せず、見送り |
| magnitude 生成 | **据え置き** | 同上。`0.5 + 0.5 * conviction` は v2.6 でも維持 |
| expected_range 幅 | **置換** | 無相関 (+0.026) → 実現レンジ幅ベースへ |
| expected_range 中心 | **recenter 撤去** | recenter なし 95% > 0.5x 88% > 1.0x 72% |
| テール (≥100bp) | **明示的に対象外** | 新方式でも捉えられない。警告層で扱う (§7) |

engine の理論構造に触れる変更のため **v2.6 相当**。spec 改訂 + Task Brief。

> **⚠️ 実装確定値 (PR #122)** — 本節の検証は 5 日窓 × 1.5 で行ったが、実装時に既存の
> `BaselineContext.trailing_mean_range_price` (**20 窓**平均) がそのまま使えることが
> 分かり、新フィールドを足さずに済む方を採った。窓長の差は包含率にほぼ影響しない
> (5/10/20 窓で 95–97%)。係数は半幅基準に読み替えて **`range_width_scale=1.25`**。
> 出荷形は `half_width = trailing_mean_range_price × max(1.25, floor_ratio)`、
> 中心 = `current_spot`。実装コードでのリプレイ実測は <30bp 100% / 30–100bp 86% /
> 全体 95%。**後続作業はこの確定値を参照すること** (本節の 5 日 × 1.5 ではなく)。

## 5.6 追検証: magnitude は「式の置換」では改善しない (§5.5 の訂正)

§5.5 の初版は magnitude も実現ボラベースに「置換」すると書いたが、実装方式を
比較検証した結果**それは誤り**だったので訂正する (60 観測、close_error 基準):

| magnitude 生成方式 | median | mean |
|---|---|---|
| 現行 (conviction スケール) | 11.5bp | 22.2bp |
| 直近 5 日 平均\|Δ\| | 14.7bp | 24.5bp |
| 直近 5 日 中央値\|Δ\| | 12.7bp | 23.4bp |
| **定数 6.0bp** | **10.6bp** | **21.1bp** |
| 定数 12.6bp (実現の中央値) | 12.0bp | 21.7bp |
| **常に 0 (予測放棄の下限)** | 15.1bp | **21.9bp** |

**どの方式も現行と大差なく、最良は「定数 6.0bp」。「常に 0」ですら平均誤差は現行を
下回る。** つまり magnitude という出力には情報がほとんど乗っていない。方向が当たった
日だけで見ても現行 8.8bp vs 実現ボラ方式 8.7bp とほぼ同一。

### なぜ §5.5 の推論が外れたか

点予測 (`expected_close_change_bp`) と区間予測 (`expected_range`) では最適解が違う。
close_error は L1 損失なので、最適な点予測は**条件付き中央値**であり、実現 |Δ| の
分布が右に裾を引く以上「小さめに出す」現行挙動は L1 の意味で合理的だった。
一方レンジはカバレッジが目的なので広く取るのが正しい。**同じ「幅」でも目的関数が
異なる**ことを §5.5 では見落としていた。

### 訂正後のスコープ

- **range 幅の置換が v2.6 の本丸** (45.5% → 95%、効果が大きく検証済み)。
- **magnitude は据え置き**。逆相関 (−0.282) を構造から取り除くことには正当性が
  あるが、代替 5 案がいずれも close error を改善しなかった以上、測定可能な利益の
  ない engine 変更になる。PR #122 でも `0.5 + 0.5 * conviction` を維持した。
- magnitude 出力そのものの存在意義 (情報量がほぼ無い) は、より広いスコープの論点
  として次期 planning に送る。v2.6 では触れない。

## 6. 論点D: conviction は機能している (7 月唯一の good news)

| conviction | N | 方向的中 | 平均誤差 |
|---|---|---|---|
| ≥ 0.7 | 7 | **86%** | 19.5bp |
| < 0.7 | 15 | 40% | 40.9bp |

conviction は予測の信頼度として**正しく較正されている**。7/30 の暴落日も予測時点

**運用上の含意**: conviction は position sizing の入力として使える品質がある。
execution レイヤー planning (STATUS queue #3) の設計前提として記録する。

唯一の失敗は 7/29 (conviction 0.818 で up → 実現 −26.9bp)。暴落の前兆日に高確信を
出しており、tail の予兆検知はできていない。

## 7. 論点E: 日次スナップショットの構造的限界 — 監視の不在

エンジンは 08:00 JST のスナップショットのみを入力とする。今回の暴落は **22:00 に
発生**しており、次にエンジンが世界を見たのは 10 時間後の翌朝だった。

- これは **予測精度の問題ではない** (22:00 の急変は朝の情報では原理的に予測不能)。
- 問題は、**急変が起きたことを誰にも知らせる仕組みがない**こと。7/30 22:00 の
  −321pips を検知できていれば、ユーザーは 7/31 中 (159–160 円台、含み損 −27 万円
  時点) に判断できた。実際には週末クローズ後の 8/1 に −46 万円で知ることになった。
- 7/29 の議論で「1h プロトコル化は保留が妥当」と判断したが、**その判断は
  『予測の 1h 化』についてのもので、『監視の 1h 化』は別問題**だった。前者の保留は
  今も妥当 (§6 のとおり日次予測は機能している)。後者は今回の実損が正当化する。

**提案**: 予測プロトコルには手を入れず、**独立した価格アラート**を追加する。
1h 足を定期取得し、閾値 (例: 1 時間で ±100pips、または任意の水準の上抜け/下抜け)
に触れたら通知する。既存の `fx-intraday-fetch.yml` が実証済みの取得経路なので、
cron 化 + 閾値判定 + 通知で完結する。engine / protocol 非改変。brief 1 本相当。

## 8. 設計判断の誤りについて (記録)

グリッド設計時 (7/27) に私が提示したリスク見積もりは過小だった。記録として残す:

| 私の見積もり | 実際 |
|---|---|
| 「最悪日は −147pips (7/2)」 | 7/30 に **−542pips** (3.7 倍) |
| 「撤退時の損失 −18 万円」 | 週末クローズ時点で **−45.9 万円** (2.6 倍) |
| 「ショック時の瞬間含み損 最大 10 万円」(1h 検証後に更新) | **−48.2 万円** (4.8 倍) |

原因は、3 ヶ月 (55 営業日) の観測レンジ内で最悪値を「起こりうる最悪」として扱った
こと。標本が短いほど tail は必ず過小に出る。**推定に使った窓の外側の事象を、窓の
統計で語ってはいけない**という初歩的な誤りで、engine 側の §4–5 (レンジ/magnitude の
tail 過小) と同じ構造の失敗をしている。

資金管理が機能したこと (維持率 503%、ロスカットまで約 2,640pips) は、ユーザーが
余力を厚く取っていたことによるもので、私の見積もり精度によるものではない。

**再発防止として encode すること**: リスク提示の際は「観測窓内の最悪値」ではなく

## 10. 追補: v2.6 初運用週の事後検証 (2026-08-03〜08-07)

本節は 2026-07 レビューの**事後検証**。v2.6 (PR #122) が最初に実運用された週の
ログを分析し、§4–5.6 の処方箋が効いたか、何が残ったかを記録する。
週報: `docs/reports/fx_weekly_report_20260803_20260807.md`。

### 10.1 レンジ改修は効いた。ただし代償が定量化された

Range 的中 **4/4 = 100%** (全 variant)。7 月月次 45.5%、前週 50% からの跳躍で、
PR #122 のリプレイ予測 (95%) と整合する。**§4 の処方箋は実運用で再現した。**

一方、包含の「質」を測ると幅の過剰が見える (alpha):

| 日 | レンジ全幅 | 実現日中レンジ | 過剰倍率 | 終値のレンジ内位置 |
|---|---|---|---|---|
| 8/3 | 259pips | 267pips | 1.0x | 34% |
| 8/4 | 277pips | 80pips | **3.5x** | 70% |
| 8/5 | 281pips | 60pips | **4.7x** | 51% |
| 8/6 | 280pips | 101pips | **2.8x** | 74% |

中央値 **3.1x** (v2.5 期の 7 月は 0.6–1.0x)。終値は常に中央付近で、端まで
72–138pips の余裕があった。**包含率を買って情報量を売った**トレードオフが数字で
確認できる。原因は `trailing_mean_range_price` が単純 20 窓平均で、7/30 の 577pips
が母数に残るため (8 月下旬まで継続)。

**対処案**: 単純平均 → 中央値 / trimmed mean。ただし **9 月の月次レビューまで
着手しない** — v2.6 の評価済み観測はまだ 4 日で、母数が足りない。

### 10.2 方向が転換に追随しなかった経路 (初版の因果主張を撤回)

**⚠️ 初版の訂正 (2026-08-09、PR #123 レビュー指摘による)。** 初版は本節を
「state 分類器が転換点 (exhaustion) を検出できない」と題し、8/3 の実現 state が
`exhaustion` だったのにエンジンが `fire` と判定したため down を出し続けた、と
書いた。**この因果は成立しない。以下 2 点が誤りだった。**

#### 誤り 1: state は方向を駆動していない

`build_ugh_variant_forecast` の実装では、`forecast_direction` は

```
pre_expansion_bp = e_star × trailing_mean_abs_close_change_bp × (0.5 + 0.5×conviction)
forecast_direction = _direction_from_bp_with_epsilon(pre_expansion_bp, ..., config)
```

で決まり、`state_res.dominant_state` は **レコードに記録されるだけで方向計算に
入らない**。したがって「fire と判定したから down を出した」は誤り。dominant_state
に確信度下限を設けても FLAT にはならない (初版 §10.6 の処方箋 2 は無効)。

正しい記述: **8/3–8/7 の down は `e_star` が全日マイナス (−0.158〜−0.513) だった
ことによる。** state が同時に fire だったのは、同じ signal features から独立に
計算された並行観測であって、原因ではない。

#### 誤り 2: `exhaustion` を転換の ground truth として使った

`classify_realized_state` は docstring で **"coarse v1 proxy"** かつ
**"direction-agnostic OHLC alone"** と明示されており、さらに
**`failure` は `exhaustion` と区別できないため出力されない**と書かれている。
つまり `exhaustion` ラベルは「売り手が枯れた」「転換した」ことの証拠ではなく、
「大きめのレンジを出したが終値が伸びなかった日」以上を意味しない。

実証的にも外れている: **7/31 の実現 `exhaustion` の翌営業日、8/3 に 155.21 まで
さらに 236pips 下落した。** 転換していない。

加えて自己矛盾があった — 同じ PR の週報で「8/3 の下ヒゲ = 売り枯れ」という読みを
介入を理由に撤回しておきながら、本節ではその読みを前提に「転換シグナルを 2 回
見逃した」と論じ、下ヒゲ / body 比を予測側の入力にせよと処方していた。

#### 同じ誤りを 2 度している (これが本当の教訓)

| | 誤った推論 | 実際 |
|---|---|---|
| 週報 初版 | 下ヒゲ 195pips → 売り枯れ → 底打ち | 日米協調介入 |
| findings §10 初版 | exhaustion ラベル → 転換点 → state 分類器を直せ | ラベルは方向不可知の粗い heuristic |

どちらも **価格パターンから因果を読んだ**もの。パターンは事実だが、原因は
パターンからは出てこない。`fx-market-context` skill を新設したのはこの穴を塞ぐため
だが、**engine 側の診断でも同じ規律が要る** — 実現ラベルは「何が起きたか」の
粗い記述であって、「なぜ起きたか」でも「次にどうなるか」でもない。

#### 事実として言えること

- 8/3–8/7 の全日で **`e_star` がマイナス** (−0.158〜−0.513)。ただし出力方向は
  down 固定ではない — β/δ は 8/5 と 8/7 に FLAT を出している。epsilon 判定が
  小さな負値を FLAT に落とすため、**「生シグナルは一貫して弱気」と「全 variant が
  down を出し続けた」は別の主張**であり、後者は事実に反する。市場は 8/3 の
  155.21 から 158.42 まで反発したため、down を出した日のうち 8/4 (+35.0bp) と
  8/6 (+43.1bp) を外した。
- 予測 state も全日 fire で固定。実現 state (exhaustion / expansion / setup) とは
  一致せず、stC は 0%。
- **両者が同時に転換に追随しなかったのは事実だが、片方がもう片方を引き起こした
  証拠はない。** 共通の上流 (signal features / projection 入力) を疑うのが筋。

### 10.3 state 確率がほぼフラット — 診断上の観測 (方向とは別経路)

予測 state の確率分布は判別が成立していない水準だった (alpha):

| 日 | fire | setup | failure | expansion | 最大確率 |
|---|---|---|---|---|---|
| 8/3 | 0.268 | 0.255 | 0.178 | 0.112 | **0.268** |
| 8/5 | 0.340 | 0.160 | 0.245 | 0.135 | **0.340** |

6 状態で最大 0.27–0.34。**ただし §10.2 のとおり dominant_state は方向計算に
入らない**ため、これは方向精度の説明にはならない。

⚠️ **初版はここで「hysteresis の FLAT 退避経路」を state の下流として挙げたが、
これも誤り** (PR #123 レビュー)。repo 全体を検索しても forecast 側で
`dominant_state` を消費する箇所はなく、FLAT は
`_direction_from_bp_with_epsilon` の epsilon 判定だけで決まる。実証的にも、
β/δ が FLAT を出した日の state は α/γ と同じ `fire` であり、**同じ state から
異なる出力が出ている**以上 state は原因ではない。`dominant_state` の実際の
consumer は評価 (stC / state_proxy_hit)、集計・レポート、次期 state 計算の
tie-break のみ。したがって本節は **stC の診断値としてのみ**意味を持つ。

### 10.4 conviction 較正は条件付きの可能性 (n=4、断定不可)

| | 今週 (n=4) | 7 月 (参考) |
|---|---|---|
| conviction 高 | **0/2 hit**、平均誤差 55.0bp | ≥0.7 で 6/7 hit |
| conviction 低 | **2/2 hit**、平均誤差 11.7bp | <0.7 で 6/16 hit |

§6 の「conviction は正しく較正されている」と逆向き。**n=4 では偶然と区別できない**
ので、観測の記録に留める。

初版はこれを「state 誤認下では conviction が逆指標になる」と説明したが、§10.2 で
state → 方向の因果が否定された以上、その説明は成り立たない。conviction は
`e_star` と同じ projection 経路にあり、方向にも magnitude にも直接効くので、
**仮説を立てるなら projection 側**である。9 月の月次で標本を足してから判定する。

### 10.5 stC が測っているもの

7 月時点では stC を「実現レンジ幅の regime を先読みできたか」と解釈した (§5.5)。
今週の観測を踏まえた、より安全な言い方は **「予測 state と、OHLC から機械的に付けた
粗いラベルとの一致率」** — それ以上でも以下でもない。低いことは予測 state が実現の
レンジ/body 形状と噛み合っていないことを示すが、**「転換を見逃した」とまでは
言えない** (実現ラベル自体が転換を判定していないため)。

### 10.6 次の論点

1. **方向が転換に追随しない件は `projection` / `e_star` 経路の問題として扱う** —
   初版はこれを state 分類器の課題として書いたが誤り (§10.2)。8/3–8/7 の down は
   e_star がマイナスで固定されたことによる。調査対象は e_star を構成する
   signal features と、その更新が急変後にどれだけ速く効くか。
   7/13 週の「退避解除の遅れ」、7/27 週の「fire/down 固執」と同じ症状に見えるが、
   **同じ経路かどうかも未検証**であり、まず経路の切り分けから始める。
2. **state 分類器の改善は stC 専用の課題として独立に扱う** — 方向にも FLAT にも
   効かない (§10.2 / §10.3)。改善しても動くのは stC と state 別集計の解釈だけ
   なので、優先度は 1 より明確に下。
3. **レンジ幅の robust statistic 化** (§10.1) — 9 月の月次レビューで検証。
4. **conviction 較正の再判定** (§10.4) — n=4 では判定不能。標本待ち。
