## 今週の構造的観測: provider の日足遅延が forecast を 1 日消し、執行層ゲートの除外機構を初めて呼ぶ

これまでの Saturday artifact 欠落 (8/29・9/5・9/12) はすべて **cron 遅延**で最終 retry が JST 土曜に落ちた
ケースで、#130 の繰り越し経路 (金曜の完全 batch があれば `as_of` を金曜に戻す) が 10/16 まで 5 週連続で救って
きた。今週は別の経路で落ちた:

1. 10/23 (金) 19:16 JST に記録された初回 run で、alpha_vantage の最新完了窓の終端が **10/22 08:00 のまま**
   (10/22 の日足 = 10/22 08:00 → 10/23 08:00 の窓が未公表)。automation Step 2 の 1 営業日 provider-lag fallback
   どおり `as_of` を 10/22 に繰り下げ → 10/22 batch は既にあるので `idempotent_skip`。21:41 JST の
   2 回目も同じ。この時点で 10/23 の forecast は存在しない。
2. 00:47 JST (土) の最終 retry は 10/24 が営業日でないため #130 の繰り越し経路に入るが、**繰り越す先の 10/23
   batch が無い**ので `_fail`: 「Today (2026-10-24 JST) is not a protocol business day, and the previous business
   day (2026-10-23 JST) has no complete forecast batch to carry over.」
3. 結果: 10/23 の forecast・判断は永久に無い (catch-up は outcome を埋めるが forecast は作らない)、10/22 の
   outcome は日足が出るまで未確定、weekly v2 と執行層 artifact は生成されない。PRICE-ALERT の stall 検知
   (22:45 JST「no 2026-10-23 forecast」) は正しく発報した。

含意は 3 つ。(a) **運用**: 遅延が原因でなく provider 側の公表遅れなので、cron を早めても防げない。金曜に
provider が遅れた場合の第 3 の経路 — 最終 retry で yahoo fallback に切り替えて前日の bar を取る、または金曜
